# 03_GPU体系结构

第一部分是 GPU 学习。我以 curryGPU 这个工程为对象，按图从左到右：最外层是整机，命令处理器把线程块分发到各个 SM；中间是 SM，四个 subcore 共享访存和特殊功能单元；右边是我重点读的 subcore，每个 subcore 管理十六个 warp。读下来最核心的一点是：GPU 不靠单线程快，而是靠每拍从多个 warp 里挑一个能发射的来掩盖访存延迟，调度器、scoreboard 和独立线程调度都是围绕这件事设计的。

---

# 04_为什么重构

读懂结构之后，我对 subcore 的 RTL 做了一次流水线重构。原来的 RTL 功能是正确的，问题在于结构不清晰：发射路径是一整条组合链，级与级之间直接组合读取对方的内部状态，挡住发射的条件散落在六千多行的顶层里，还有同一 warp 只能隔拍发射这样的隐式约定。右边是重构的目标结构。另外，在此之前我还探索过加速器模拟器和 workload trace 压缩，这条线需要定制 NPU 的系统经验做支撑，我目前还缺这方面的积累，所以先暂缓，计划在后续接触到机柜级 NPU 之后再继续。

---

# 05_subcore目标结构

这一页是重构后 subcore 的具体结构。上面是七个大级：取指、译码、发射、分派、操作数、执行和写回，每一级是一个独立的模块。下面是三个关键设计。第一，操作数级里有四张预约表，读口、写回拍、执行单元出口和入口，资源冲突从同一拍看忙不忙，改成了提前按拍预约。第二，访存、特殊函数、分支这些延迟不固定的指令，经过分派级的队列进入各自的前门模块，用 credit 控制：发射时减一，前门读完操作数后再加回，credit 等于队列深度，所以入队一定成功。第三，级与级之间只走寄存过的事件，目的级下一拍才看到，唯一的反向信号是在途掩码。总的原则就是：每一级持有自己的状态，级间只走寄存过的事件。目前 RTL 已经按这个结构实现，只有常量前门还没做。

---

# 06_重构方法与结果

方法上是先定结构、再动代码：先写结构规范、画出目标图，对照目标图列出六十三项修改，然后在行为不变的前提下按级搬迁，每次提交都跑完整的 VCS 验收并记录周期变化。最终一共一百三十次提交，顶层代码减少了百分之四十三，新建了十六个模块。过程中还顺带修掉了一些真实缺陷，比如 shared memory 的读后写漏洞，在七千多次重试里有九十六次读到了新值。但重构中我也发现，有些问题功能验证全部通过也抓不到，这就是第二部分的出发点。

---

# 07_领域现状

进入第二部分，先简单看一下领域现状。AI 生成 RTL 的工作大致分四条路线，区别主要在于给模型什么输入。看右边的结果：单个模块已经能做到九成以上，一到 SoC 和子系统级就掉到六成、三成，到流水线和层次化设计，所有模型都失败了。文献里有一个规律：换一种中间表示，成功率能从百分之三提到百分之八十八，换更强的模型提升不到一点二五倍。而现有工作检查正确性时只看端口输入输出，不看逻辑在哪一级、状态归谁、时序对不对。

---

# 08_问题的提出

这个空白我在 subcore 上实际碰到了。这个 subcore 有十万多行 Verilog，大部分由 AI agent 编写和重构，每次提交都跑完整的功能验证，但功能全部通过，问题照样漏过去。举一个例子：有一次提交把一段逻辑从一个模块搬到另一个模块，说明写的是行为不变，结果也确实是周期数完全不变；但搬完之后，有一段本该属于上一级的逻辑落进了 S4，和设计图对不上，这个偏差一路带过了好几次提交，现有检查都没有发现。第二类是时序，有两次提交让程序慢了百分之六到八，恰好落在性能模型的误差范围内。第三类是验证手段自己失效了，比如验收脚本只看有没有打印 PASS，漏掉了实际发生的硬件故障。

---

# 09_已实现的检查工具

针对这三类问题，我已经实现了三种检查工具，都在 subcore 上日常运行。第一是逐指令比对，逐线程比较 RTL 和功能模型执行的指令序列，只报告第一处分歧；一个有错的发射改动，在三个用例的第二、三条指令处就被报了出来。第二是网表结构检查，一份结构数据同时生成流水线图、给 AI 的约束清单和检查器，读 Verilator 的网表，核对层次、边界寄存器和级间连线，没有登记的触发器和连线一律报出；人为注入的十六种缺陷全部被拦下，第一次在真实 RTL 上运行就发现了五处结构分歧，上一页的结构偏离就是其中之一，目前六个流水级都接入了门禁。第三是断言和验收门禁，检查每个断言文件是否真的被运行，验收要求没有硬件故障并且用例自己打印 PASS，断言文件从十七个增加到五十个全部运行。时序方面的逐周期检查，则用接下来两页的 FML 来做。

# 10_FML框架结构

FML 是一套周期级建模框架，由我的合作者开发，模型用 Rust 写。它的基本结构是模块和事件：每个模块声明自己拥有的状态，里面的任务由时钟沿或者事件触发，模块之间只通过带延迟的事件通信。下面这段代码来自官方示例，可以看到状态、时钟入口、事件出口都是显式声明的。它适合作结构规格有四点原因：状态归属写在结构里；级间传递是显式的；同一拍内的依赖必须说清楚，虚拟机在加载时就推出执行顺序，有歧义直接拒绝；并行运行结果确定，可以作比对参照。合作者已经用它逐周期复现了 GPGPU-Sim，在 rodinia 的十一个基准上和原版完全一致，速度还更快。

---

# 11_路线B实验

我在 FML 上做的工作是路线 B 实验。左边是边界规格的样子：以取指和译码级为例，每个 subcore 拆成 Fetch 和 Decode 两个模块，规格写清每个模块拥有哪些寄存器、每拍按什么顺序更新、允许哪些同拍路径、相对参照模型有哪些偏差和代价。实验流程是：规格先和 GPGPU-Sim 逐周期对齐，再只把规格和接口交给 AI，让它独立写 RTL，最后在边界上逐周期比对。结果是，规格在一百三十六万个周期上和参照一致；按 subcore 拆分边界后，综合出的最长逻辑路径从四百三十五级降到四十二级；四个模块集成成完整的 subcore，在五百五十一万个周期上通过。还有两个发现：切边界时暴露了顺序模型里看不见的同拍组合环；每个模块各自验收都通过，集成时才暴露出一个接口缺口，说明边界规格本身也需要被检查。

# 12_设计验证框架

第三部分是公司学习。在公司期间，我参与了三个芯片项目，另外系统学习了一个 SoC 项目的设计，出于保密，这里用 A 到 D 代称。我把这些经验归纳成芯片设计验证的五层流程。大家看右边的点：A 和 B 集中在设计层，C 和 D 集中在验证、多模式仿真和可测性，四个项目合起来覆盖了完整的链条。这五层里我感受最深的是最上面这一层：规格是唯一的来源，设计和验证都从它派生。

---

# 13_设计侧

先看设计侧。项目 A 是我学习的一个 RISC-V SoC，从它身上我看懂了一颗 SoC 是怎么搭起来的：处理器核、总线、存储器大多是第三方 IP，公司的工作主要是集成；每个 IP 单独一个目录，带自己的文件清单；和工艺相关的单元单独放一层。项目 B 是一个图像处理 DSP，我负责它验证环境里的 scoreboard，也就是自动比对输出的部分。要写比对就得先把设计读透，所以我学到了一个模块应该怎么写：每个任务都是工作态加等待态成对出现，状态编码直接拿来做时钟门控，数据通路统一用握手流水。这种写法后来直接用在了 GPU 重构里，subcore 完成信号的设计就是参考这个 DSP 做的。

---

# 14_验证侧

再看验证侧。左边是项目 C 验证环境的目录结构：顶层把被测设计、模拟行为模型和接口接在一起；环境目录放驱动、参考模型、寄存器宏和时序检查；所有用例继承同一个基类，每个用例只写配置和激励检查两个任务；运行目录放 Makefile、分组清单和回归脚本，通过开关切换后仿、扫描模式、工艺角和随机种子。在项目 C 里我负责三块验证：AL 光谱通道的数据通路、数模控制信号的时序检查，以及部分看门狗。在项目 D 里我主要协助做数模混合仿真，用的是 Synopsys 和 Cadence 的工具，难点在配置，CPU 侧的启动和固件要求、模拟侧的电路配置都要对上，所以花了很多时间和两边的同事沟通。

# 15_总结与计划

最后是总结和计划。这一年我完成了 GPU 体系结构学习和 subcore 流水线重构，实现了三种检查工具，在 FML 上完成了路线 B 实验，也通过公司项目掌握了设计验证的流程。公司流程给我的研究带来的启发是：规格是唯一来源，验证要分层，级与级之间传递什么必须写清楚。后续计划主要有四点：以 FML 为底座建立结构规范；建立可以量化的验收标准，Hazard3 会是第一个外部验证对象；更长远地，深入编译器，探索软硬件协同的 AI 架构设计；最后是学位论文的撰写。具体节奏会根据实验进展和导师的意见调整。我的汇报就到这里，恳请各位老师批评指正。
